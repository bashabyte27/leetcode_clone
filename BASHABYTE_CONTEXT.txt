==================================================
1. PROJECT OVERVIEW
==================================================
BashaByte is the current Django-based coding platform in this repository. It is a LeetCode-style practice site with additional capabilities for learning, discussion, contests, and premium access. The app is not a generic blog or admin-only project; it is built around users solving coding problems, submitting solutions, reviewing results, and interacting with community content.

Main purpose:
- Problem practice and coding challenge workflow
- Submission and judging against test cases
- User profiles and progress tracking
- Courses, study plans, discussions, and contests
- Premium access controls for paid features

Current technology stack:
- Backend: Django 5.2
- Frontend: Django templates + custom CSS + vanilla JavaScript
- Database: SQLite by default for local development; PostgreSQL is supported via DATABASE_URL and dj-database-url
- Authentication: Django auth framework integrated with a custom Users model
- Execution engine: Judge0 HTTP API
- Deployment support: Gunicorn, WhiteNoise, Render host configuration, environment variables via python-dotenv
- Additional libraries: requests, resend, pandas/openpyxl, Pillow, dj-database-url, psycopg2-binary

Current frontend approach:
- Server-rendered templates dominate the app
- Problem page uses a full-screen two-panel/three-panel layout with Monaco editor embedded in a custom page shell
- JavaScript uses fetch() for AJAX interactions and partial HTML reloads
- The main interactive page is templates/problems/problem_detail.html plus static/js/problem_detail.js
- Base UI styling is split across static/css and a Bootstrap-based base template; the problem page uses custom CSS and direct DOM behavior

Database:
- Local default database is db.sqlite3 in the project root
- The project is prepared for PostgreSQL in production via DATABASE_URL and postgres-friendly deployment settings
- Models are spread across multiple Django apps, with all app-level data tied together by FK relationships to users.Users and problems.Problem

Code execution technology:
- The execution layer uses Judge0 via HTTP requests
- Judge0 is configured via settings.JUDGE0_URL, JUDGE0_AUTH_TOKEN, and JUDGE0_TIMEOUT
- Judge0 is used for both:
  - Run code against sample cases
  - Submit code against all hidden/visible test cases
- Request/response logic is centered in submissions/judge0.py and submissions/judge.py

Deployment-related technologies if present:
- whitenoise.middleware.WhiteNoiseMiddleware is enabled
- STATICFILES_STORAGE uses WhiteNoise manifest storage
- STATIC_ROOT = BASE_DIR / 'staticfiles'
- MEDIA_ROOT = BASE_DIR / 'media'
- ALLOWED_HOSTS accepts localhost, 127.0.0.1, testserver, .onrender.com, and additional env-provided hosts
- CSRF_TRUSTED_ORIGINS includes Render hosts
- Deployment is clearly oriented toward Render hosting, but the project is still primarily a local Django app in this repo

Important models and field details:
- Users.id is a UUIDField primary key.
- Users.user_name is unique and validated; email is the Django auth username field.
- Users.role is a TextChoices field with USER / MODERATOR / ADMIN.
- Problem.order_num is unique and acts like the LeetCode numeric ID.
- Problem.slug is unique and is the URL slug used in routes.
- TestCase uses unique_together = (problem, order_num) and supports sample vs hidden case separation.
- SubmissionStatusChoices is a central shared enum imported by contests models.
- Discussion.vote_count and Comment.vote_count are denormalized counters updated by vote logic.
- UserStats is a denormalized stats table with solved-by-difficulty counts and contest_rating.
- UserSolvedProblem is a denormalized O(1) solved lookup table.
- Premium subscription records store Stripe IDs and billing period metadata.

Important keys and relationships:
- ForeignKeys are the main relationship mechanism across apps.
- OneToOneFields are used for UserProfile, UserStats, Editorial, EmailVerificationToken.
- ManyToManyFields are explicit through-model relations for tags and companies.
- unique_together is heavily used for integrity: user + problem, problem + tag, contest + problem, user + contest, etc.

Important indexes / constraints:
- Users indexes cover email, user_name, role+is_active, is_premium+is_active
- Problem indexes cover difficulty+is_active, is_premium+is_active, slug, order_num
- Submission indexes cover user+problem, user+status, problem+status, problem+language+status, submitted_at
- Contest indexes cover start_time and contest_type ordering
- Premium indexes cover user+status and status+current_period_end
- Generic voting indexes cover content_type + object_id and user

Important dependency pattern:
- Many app models depend on users.Users and problems.Problem.
- The execution flow depends on Problem + Language + TestCase + Submission.
- Contest logic wraps Submission without duplicating the full problem model.

4. USER AND AUTHENTICATION SYSTEM
==================================================
Current custom user model:
- Custom auth model is users.Users.
- It inherits AbstractBaseUser, PermissionsMixin.
- AUTH_USER_MODEL = 'users.Users' is set in leetcode_project/settings.py.
- USERNAME_FIELD is email; REQUIRED_FIELDS is ['user_name'].
- Unique username and unique email are enforced.
- The user has fields like is_verified, is_premium, is_active, role, avatar_url, created_at, updated_at.

Authentication flow:
- Django auth middleware handles sessions.
- Login uses Django's login(request, user) and redirects to the problem list after successful login.
- Logout uses django.contrib.auth.logout() and redirects to home page.
- The app uses standard Django session cookies and request.user.

Registration:
- users/views.py register_view creates a User from RegisterForm.
- Current implementation temporarily bypasses email OTP flow by immediately creating the user and redirecting to login.
- There are OTP utilities in place for email verification and password reset, but the active registration path does not require email verification before account creation.
- Resend emails are attempted only if a provider key is configured; otherwise the OTP is generated but not sent.

Login:
- users/views.py login_view checks if request.user.is_authenticated and then redirects to problems:problem_list.
- If form is valid, login(request, form.user_cache) is called.
- This is a standard Django auth login with a custom user model.

Logout:
- users/views.py logout_view calls logout(request) and redirects to home.

Email/password verification:
- EmailVerificationToken and PasswordResetToken models exist.
- Password reset flow is implemented in users/views.py reset_password using OTP and session-based step 2 flow.
- The project has resend API support, but the app currently does not enforce email verification in the main registration route.

OAuth/social auth:
- OAuthProvider model exists with provider_name, provider_user_id, access_token, refresh_token, expires_at.
- It supports Google, GitHub, LinkedIn style providers.
- There is no active OAuth login implementation in the current URLs or views; the model is ready for future integration.

Existing user roles:
- UserRoleChoices: USER, MODERATOR, ADMIN
- Role affects moderator-style capabilities and admin access in principle.
- The current app uses role metadata rather than heavy permission enforcement in every view.

Profiles:
- UserProfile is a 1:1 profile table with bio, location, website, GitHub, LinkedIn, Twitter, company.
- profile_view loads profile data and public stats for a target user.
- Profile pages compute solved counts, acceptance rate, total problems, and placement among users.

Sessions:
- Django session auth handles login state.
- There is also a custom Session model in users/models.py that tracks per-user session metadata, token hash, user agent, IP address, device type, expiry.
- This is more of a supplemental audit/session model than the core auth session backend.

Permissions:
- Django PermissionsMixin is present on Users.
- The app uses is_staff and is_superuser through Django admin and custom role logic.
- Most user access gating is done by @login_required and by checking request.user in views, not by a deep custom permission layer.

Global platform functionality:
- The custom user model and the Django auth/session system are global platform features.
- They affect all apps, including submissions, problems, discussions, premium, and contests.

This is the foundation of the platform and the main user-facing practice flow.

Problem lifecycle:
User
↓
Problem list
↓
Problem detail page
↓
Monaco editor
↓
Run / Submit
↓
Submission system
↓
Code execution
↓
Result
↓
Submission history

Problem model:
- problems.models.Problem contains the problem catalog entry.
- Fields include order_num, title, slug, description, difficulty, acceptance_rate, likes, dislikes, is_premium, is_active, created_by.
- Difficulty uses DifficultyChoices: easy / medium / hard.
- Problems are ordered by order_num and can be filtered by active status and difficulty.
- Problem.slug is the public URL slug.

Difficulty:
- easy, medium, hard via DifficultyChoices.
- Profiles and user stats aggregate solved counts by difficulty.

Topics / tags:
- Tag model stores tag names and slug.
- ProblemTag is the join table between Problem and Tag.
- Tags appear on the problem detail page as topic pills.

Companies:
- Company model stores company names, slug, and logo_url.
- ProblemCompany stores frequency values for company-question association.

Test cases:
- TestCase is attached to a problem and contains input_data, expected_output, is_sample, explanation, order_num.
- Test cases are used in both sample display and judge execution.
- They are unique per problem + order_num.
- Sample cases are shown on the problem page; hidden full cases are used for submit-flow evaluation.

Supported languages:
- Language model centralizes language metadata.
- Languages are seeded by import_problems.py with Python, Java, C++, C, JavaScript, Go, Rust.
- Each Language has a name, slug, version, judge_id, and is_active.
- judge_id matches Judge0 language IDs.

URLs:
- /problems/ -> list page
- /problems/shuffle/ -> random problem redirect
- /problems/<slug>/ -> problem detail page
- /problems/problems-panel/ -> side panel HTML list
- /problems/<slug>/editorial -> editorial partial
- /problems/<slug>/submissions -> submission history partial
- /problems/problems -> legacy/secondary route present in urls.py as a direct alias to another partial loader

Views:
- problem_list: builds the main list view, plus solved counts and progress pills
- problem_detail: renders the full interactive problem page and sample cases
- shuffle_problem: sends user to a random active problem
- problem_get_list: loads the problem list panel for the drawer UI
- editorial: loads editorial partial
- submission_history: user-specific history for a problem

Services:
- The Problem module itself does not contain complex business logic beyond access and display.
- Most execution/workflow logic sits in the submissions app, but the problem page is the integration point for editor, sample case display, and AJAX submission requests.

Templates:
- templates/problems/problem_detail.html is the main interactive problem page
- It includes problem description, tabs for Description / Editorial / Discussion / Submissions
- It includes the Monaco editor, theme toggle, timer, language selector, case panes, and result panel

JavaScript:
- static/js/problem_detail.js is the main client-side orchestrator
- It handles:
  - Monaco setup
  - theme switching
  - editor autosave
  - timer logic
  - run and submit requests
  - result rendering
  - discussion tab fetching
  - code error line highlighting
- It communicates with /submissions/run/<slug>/ and /submissions/submit/<slug>/ via fetch()

Execution flow:
- The user opens a problem page.
- The page loads sample cases and a preloaded editor state.
- The user selects a language and writes code.
- Clicking Run triggers a POST to /submissions/run/<problem_slug>/.
- The backend validates input and code safety, fetches sample cases, executes via Judge0, and returns per-test-case results.
- Clicking Submit triggers POST to /submissions/submit/<problem_slug>/.
- The backend creates a Submission row, judges it against all test cases, stores results, and returns final status and per-case results.

Judge0 integration:
- Judge0 is called from submissions/judge0.py and submissions/judge.py.
- It maps Judge0 result IDs to BashaByte statuses: accepted, wrong_answer, time_limit_exceeded, compile_error, runtime_error, internal_error.
- Batch execution is used for submit mode; single execution is used for run mode.

Results storage:
- Submission stores the aggregate metadata for the full attempt.
- SubmissionResult stores each test-case result, including actual_output, expected_output, status, runtime_ms, memory_kb.
- CodeRun stores ad-hoc run history without affecting stats.
- UserSolvedProblem is denormalized to provide cached solved state.

Stable working parts that should not be unnecessarily rewritten:
- Problem/detail page structure and Monaco-driven execution flow
- Problem model + language/testcase schema
- Submission result flow and Judge0 mapping
- URL naming used by the frontend fetches
- Problem list and detail page conventions around slug-based navigation

6. SUBMISSIONS / CODE EXECUTION
==================================================
Submission model:
- submissions.models.Submission is the main user attempt record.
- Fields include user, problem, language, code, status, runtime_ms, memory_kb, solve_time_seconds, submitted_at.
- It stores the final result for a run or submit attempt.
- The model has indexes for user+problem, user+status, problem+status, problem+language+status, and submitted_at.
- Submission.is_accepted is a convenience property.

Run vs Submit behavior:
- Run mode is for custom sample validation in the editor and is not considered a formal accepted submission.
- Submit mode creates a Submission row and tests the program against all relevant test cases.
- Run uses CodeRun semantics for temporary output checks; Submit persists a judged attempt and influences solved stats.

Execution request architecture:
- /submissions/run/<problem_slug>/ executes the run_code view.
- /submissions/submit/<problem_slug>/ executes the submit_code view.
- Both parse JSON body payloads and expect code + language + optional custom input or elapsed time.
- Both validate problem existence, active status, and language existence.
- Both perform code safety checks before execution.

Judge0 or execution provider:
- submission/judge0.py wraps requests to Judge0 endpoints.
- execute_single() submits a single code execution and waits for the result.
- execute_batch() submits multiple test cases in one batch and polls for completion.
- This is the current execution provider used by the platform.

Status handling:
- The main mapping lives in submissions/judge.py JUDGE0_STATUS_MAP.
- This maps Judge0 status IDs to BashaByte statuses:
  - accepted
  - wrong_answer
  - time_limit_exceeded
  - compile_error
  - runtime_error
  - internal_error
- The backend stops at the first failing test case to follow a LeetCode-like behavior.

Output/error handling:
- Output is compared against expected_output with newline normalization.
- For compile errors: compiler output or stderr is surfaced.
- For runtime errors: stderr or compile_output is surfaced.
- For wrong answer: stdout is captured and compared to expected output.
- For time limit: runtime_ms is surfaced and execution result is marked accordingly.

Time and memory limits:
- Judge0 integration is configured via the global JUDGE0_TIMEOUT settings.
- memory_kb is captured if Judge0 provides it.
- the project is currently relying on Judge0's own limit system rather than a custom per-problem limiter in Django.

Accepted / Wrong Answer / etc. handling:
- Accepted submissions set status=accepted.
- The final submission status is the first failing status encountered when processing test cases in order.
- SubmissionResult rows capture the result for each test case individually.
- If a user solves a problem, the project also tracks solved-state records via UserSolvedProblem.

Submission history:
- Each user can view their full submission history per problem via the submissions list template.
- Problem detail page includes a submissions tab and the detailed list is returned as HTML partials.
- The associated Submission rows are the canonical history trail for code attempts.

Relationships to users and problems:
- Submission.user -> users.Users
- Submission.problem -> problems.Problem
- Submission.language -> problems.Language
- SubmissionResult.submission -> Submission
- SubmissionResult.test_case -> problems.TestCase
- CodeRun.user and CodeRun.problem are likewise connected to the same user/problem models

8. CONTESTS MODULE
==================================================
Contests are implemented as a distinct app but are not yet feature-complete in the visible views.

Contest model:
- Contest contains title, slug, description, contest_type, start_time, end_time, is_virtual, is_published, created_by
- The app supports contest types: weekly, biweekly, virtual, special
- Duration is computed from start_time and end_time via Contest.duration_minutes

Contest problems:
- ContestProblem links a Contest to a Problem and includes order_num and points.
- It prevents duplicate problems in the same contest and duplicate ordering positions.

Participants and rankings:
- ContestParticipant stores rank, score, penalty_minutes, finish_time, registered_at for a user in a contest.
- Unique_together = (user, contest)
- Participant is the person-level contest participation record

Contest submissions:
- ContestSubmission links a ContestParticipant and a ContestProblem to a single Submission object using OneToOneField.
- This allows one standardized Submission to support a contest entry while still giving contest score metadata.
- ContestSubmission has score_gained, is_accepted, penalty_minutes.

Contest ratings:
- ContestRating stores user rating before and after a contest, along with delta and rank.
- This mirrors ELO-style ranking history and updates user stats in the broader platform model.

Important relationships:
- Contest -> ContestProblem -> Problem
- ContestParticipant -> User
- ContestSubmission -> Submission
- ContestRating -> User

Current status:
- The models are well-defined, but the actual contest UI/logic is minimal in the current repo; contest_list in contests/views.py is a stub returning a simple HttpResponse.

9. DISCUSSIONS MODULE
==================================================
The discussions app implements community discussion around a problem.

Discussion model:
- Discussion is attached to a Problem and a User.
- It has title, content, discussion_type, optional language, views, vote_count, comment_count, is_pinned, is_hidden, created_at, updated_at.
- discussion_type can be general, solution, question, editorial.
- There is a lazy-created general discussion thread per problem.

Comment model:
- Comment is attached to a Discussion and User.
- It supports a single-level reply hierarchy via parent = ForeignKey('self').
- Comments are nested only one level deep in practice.

Vote model:
- Vote is generic, using Django ContentType + GenericForeignKey for both Discussion and Comment.
- Voting uses upvote (+1) and downvote (-1).
- The total vote_count is recalculated from Vote rows before returning response data.

Current workflow:
- The problem detail page loads the discussion tab via AJAX.
- _get_discussion() creates a general discussion thread lazily per problem if it does not exist.
- post_comment() creates a top-level comment or reply.
- vote_comment() toggles a vote or removes it if the same vote is clicked again.

Moderation:
- There are is_hidden fields on both Discussion and Comment.
- Hidden content is filtered out from UI rendering but not deleted.
- This supports moderation without losing data.

User relations:
- Discussion.user -> Users
- Comment.user -> Users
- Vote.user -> Users

2. User opens a problem -> /problems/<slug>/ -> problem_detail.html -> JS loads editor + sample cases
3. User clicks Run -> fetch POST /submissions/run/<slug>/ -> Judge0 executes sample cases -> returns JSON results
4. User clicks Submit -> fetch POST /submissions/submit/<slug>/ -> create Submission + SubmissionResult rows -> Judge0 evaluates all cases -> returns final status and results
5. User opens discussion tab -> AJAX GET /discussions/problems/<slug>/ -> discussion HTML rendered and inserted into the tab
6. User posts a comment -> POST /discussions/problems/<slug>/comment/ -> backend creates Comment and re-renders discussion HTML

20. CURRENT LEADERBOARD AND STAFF OPERATIONS
==================================================
Leaderboard behavior:
- /leaderboard/ renders active users with accepted submissions on active problems, ranked by points, solved count, account age, and user id.
- Points remain defined in leaderboard/services.py: Easy 10, Medium 25, Hard 50; each problem counts once per user.
- The leaderboard query remains grouped and database-driven with stable pagination.

User search behavior:
- The leaderboard has a username search input using the existing /leaderboard/ route and q query parameter.
- Search is case-insensitive and uses username starts-with matching, so one character filters immediately and additional characters narrow the result.
- The static behavior in templates/leaderboard/leaderboard.html debounces input, fetches the server-rendered page, replaces the leaderboard content, preserves the URL, and removes q when cleared so the original list returns without a refresh.
- A no-result query displays User not found; an empty query restores the complete ranked list.

Blocked-user login:
- users/forms.py resolves the submitted username or email before authentication and checks Users.is_active.
- Inactive users are rejected without a session and see: Your account has been blocked. Please contact the higher authority.
- The existing login template form alert displays the acknowledgement without exposing staff details.

Staff user management and details:
- Staff routes are under /staff/ and require an authenticated user with is_staff=True.
- /staff/users/ supports username filtering while typing, profile navigation, blocking/unblocking through POST, and a POST-only delete action at /staff/users/<uuid:user_id>/delete/.
- Delete buttons use browser confirmation before submitting; deleting a Users row follows existing Django CASCADE relationships and redirects to the staff user list.
- /staff/users/<uuid:user_id>/ shows profile data, stats, solved problems from UserSolvedProblem, and paginated Submission history.
- Each staff submission row fetches the existing /submissions/detail/<int:submission_id>/ JSON endpoint. Staff access is allowed for inspection, while normal users remain restricted to their own submissions. The same runtime, memory, status, language, timestamps, percentile, code, and per-test result data are reused.

Staff problem management:
- /staff/problems/ lists problems and links each row to /staff/problems/<int:problem_id>/.
- The problem detail form edits the existing Problem fields and the existing TestCase records; the public slug is preserved when a title changes to avoid breaking slug-based URLs.
- Test cases can be bulk edited, added as new rows, or removed. JSON updates preserve existing case ids where supplied, renumber cases in list order, and delete omitted cases. The dedicated add/delete actions are /staff/problems/<int:problem_id>/test-cases/add/ and /staff/problems/<int:problem_id>/test-cases/<int:test_case_id>/delete/.
- Problem deletion is POST-only at /staff/problems/<int:problem_id>/delete/ and requires confirmation in the staff UI. Existing Problem foreign-key behavior is retained; Django cascades dependent problem content and submissions according to the current model definitions.
- Staff problem creation continues to use the existing JSON test-case format and validation helper.

Important implementation files:
- leaderboard/views.py and leaderboard/services.py: ranking, filtering, and pagination.
- templates/leaderboard/leaderboard.html: search UI, empty state, and fetch/replace behavior.
- users/forms.py and users/views.py: login validation and session creation.
- staff/views.py and staff/urls.py: staff dashboard, user operations, problem operations, and test-case operations.
- templates/staff/user_list.html, user_detail.html, problem_list.html, and problem_form.html: staff workflows and confirmation controls.
- submissions/views.py and submissions/urls.py: canonical submission history/detail JSON contract.
- users.Users, problems.Problem, problems.TestCase, submissions.Submission, submissions.SubmissionResult, and submissions.UserSolvedProblem remain the source-of-truth relationships.

Limitations and decisions:
- Search is server-authoritative and debounced rather than loading every user into the browser.
- Browser confirmation is used because the existing staff UI has no modal component.
- static/js/staff_search.js debounces staff user/problem search input, fetches the existing list route, replaces only the result panel, updates the URL, and restores the full list when the field is cleared.
- Problem deletion intentionally follows the existing CASCADE model behavior; production deployments should consider archival or protected deletion if submission retention becomes mandatory.

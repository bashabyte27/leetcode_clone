BASHABYTE PROJECT CONTEXT
==========================

Purpose
-------
BashaByte is a Django-based LeetCode-style coding practice platform. Users can
register and log in, browse programming problems, read test cases, run code
against sample tests, submit code for judging, view submission history, use
basic discussions, view profiles, and access early-stage courses, contests,
premium, and study-plan areas.

This file is a working context guide for future coding assistants. Source code
is the final authority if this file becomes stale. Do not treat historical
notes as proof of current production state.

1. PROJECT OVERVIEW
===================

Project name: BashaByte
Repository/project root: LeetcodeProject
Django settings module: leetcode_project.settings
Current branch during context creation: main
Hosting: Render production deployment
Database: PostgreSQL in normal local/production settings; GitHub Actions CI
uses SQLite only for CI isolation.
Backend: Django 5.2.x with a custom Users model.
Frontend: Django templates, CSS, vanilla JavaScript, Monaco Editor loaded by
the problem detail page, and some CDN-hosted Bootstrap assets.
External services:
- Judge0 for remote code execution.
- Resend HTTPS API for OTP email.
- Render for hosting and PostgreSQL.
- GitHub Actions for CI.

Current development stage
-------------------------
The coding-problem catalog and basic execution workflow are implemented. The
surrounding contest, premium, course, and study-plan features are incomplete
or placeholders. Automated test coverage is very low; app test modules mostly
contain empty Django TestCase scaffolding.

Important current production facts
----------------------------------
- Production problems were imported successfully.
- The deployment command now seeds the seven required Language rows before
  importing problem data.
- The current registration flow temporarily bypasses registration email OTP
  and creates users as verified. This is intentional but is not suitable as a
  permanent arbitrary-email verification solution.
- Password reset still requires the existing email OTP flow.
- Resend currently uses onboarding@resend.dev, which is a testing sender and
  is not suitable for arbitrary recipients until a verified custom domain is
  configured.
- Actual Render environment-variable values and live service health are not
  verified by this file.

4. DATABASE ARCHITECTURE
========================

Custom user and user-owned data
--------------------------------
users.Users is the AUTH_USER_MODEL. It uses a UUID primary key, email as the
USERNAME_FIELD, and user_name as a required field. It has role, verification,
premium, active/staff flags, timestamps, and optional unique mobile_no.
Users are related to:
- UserProfile: OneToOne profile.
- UserStats: OneToOne denormalized statistics.
- Session: user sessions stored by the application model.
- OAuthProvider: external OAuth provider records.
- PasswordResetToken and EmailVerificationToken: token models defined in the
  schema but not used by the current views.
- UserFollow: follower/following self-referential relationships.
- Notification and AuditLog.
- User-owned bookmarks, reports, notes, lists, submissions, discussions,
  comments, votes, contest participation, ratings, and study-plan progress.

Problem/catalog data
--------------------
problems.Language
- name: unique display name.
- slug: unique frontend/backend lookup key.
- version: optional version string.
- judge_id: Judge0 language ID stored as text.
- is_active: availability flag.

The current seeded language mapping is:
- Python: slug python, version 3.0, Judge0 71
- Java: slug java, version 17.0.6, Judge0 62
- C++: slug cpp, version 17.0.6, Judge0 54
- C: slug c, version 10.2.0, Judge0 50
- JavaScript: slug javascript, version 18.15.0, Judge0 63
- Go: slug go, version 1.18.0, Judge0 39
- Rust: slug rust, version 1.65.0, Judge0 73

problems.Problem
- order_num: unique optional catalog number.
- title, slug, description, difficulty.
- acceptance_rate, likes, dislikes, is_premium, is_active.
- nullable created_by FK to users.Users.
- ManyToMany tags through ProblemTag.
- ManyToMany companies through ProblemCompany.

Problem relationships
---------------------
- ProblemTag: Problem FK plus Tag FK; unique per problem/tag.
- ProblemCompany: Problem FK plus Company FK and frequency; unique per
  problem/company.
- TestCase: many test cases per Problem; unique problem/order_num.
- ProblemHint: many hints per Problem; unique problem/order_num.
- CodeTemplate: per-problem/per-language starter and optional solution code;
  unique problem/language.
- Editorial: optional content in practice, one-to-one Problem relation.
- DailyChallenge: Problem FK plus unique date.
- Bookmark: user FK plus Problem FK; unique user/problem.
- ProblemReport: user, Problem, optional resolver, reason/status.
- UserNote: user plus Problem; unique user/problem.
- ProblemListItem: Problem plus ProblemList.

Other app relationships to Problem
----------------------------------
- submissions.Submission.problem, CodeRun.problem, and UserSolvedProblem.problem.
- discussions.Discussion.problem.
- contests.ContestProblem.problem.
- study_plans.StudyPlanItem.problem.

Submission data
---------------
submissions.Submission belongs to a user and Problem and optionally a
Language. It stores code, status, runtime/memory values, percentiles, solve
time, and timestamp.

SubmissionResult belongs to Submission and TestCase and stores per-case
status, actual/expected output, runtime, and memory.

CodeRun belongs to a user, Problem, and optional Language. It stores one-off
run output and does not create a Submission.

UserSolvedProblem belongs to a user and Problem, optionally references the best
Submission and Language, and stores attempt/progress timestamps. The source
comments describe signal maintenance, but the full signal behavior should be
verified before changing it.

Contests
--------
- Contest has creator, time window, type, publish state.
- ContestProblem joins Contest and Problem with order and points.
- ContestParticipant joins users and contests.
- ContestSubmission connects a participant, ContestProblem, and a Submission.
- ContestRating stores per-user/per-contest rating history.

Discussions
-----------
- Discussion belongs to Problem and user; optional Language.
- Comment belongs to Discussion and user and can reply to another Comment.
- Vote uses ContentType/GenericForeignKey for Discussion or Comment targets.

Courses
-------
Courses contains title, description, duration, paid/price/rating fields and
optional image/video/attachment file fields.

Study plans
-----------
- StudyPlan is curated catalog content.
- StudyPlanItem connects a plan to a Problem by day/order.
- UserStudyPlan records enrollment.
- UserStudyPlanProgress records per-item completion and optional Submission.

Premium
-------
SubscriptionPlan, Subscription, and PaymentTransaction model premium/payment
concepts. Current source does not contain a complete Stripe client, checkout,
webhook, or reliable premium entitlement enforcement flow.

Data categories
---------------
- Core catalog: Problem, Language, Tag, Company, TestCase, Hint, Template,
  Editorial, DailyChallenge.
- User-owned: profile, stats, bookmarks, notes, submissions, discussions,
  comments, votes, contest participation, and study-plan progress.
- Temporary/session: current registration/password-reset OTP data and pending
  user/reset data are stored in Django sessions.
- Production-only values: database credentials, email/API credentials, and
  service URLs must come from environment variables and are not documented here.

5. AUTHENTICATION AND USER FLOW
===============================

Registration: current implementation
-------------------------------------
1. GET /users/register/ renders templates/users/register.html.
2. POST uses RegisterForm validation. The form validates email format,
   username format/uniqueness, email uniqueness, optional mobile format, and
   password confirmation through Django/UserCreationForm behavior.
3. The form button still has name=send-otp for compatibility, but the current
   view temporarily bypasses registration OTP.
4. On valid input, users/views.py hashes password1 with make_password, creates
   a Users row with email, user_name, mobile_no, and is_verified=True, then
   redirects to users:login.
5. No registration email is sent in the active path.

The old registration OTP code remains in users/views.py after the immediate
return so it can be restored later when a verified email domain is available.
It currently cannot be reached through this successful branch.

Login
-----
users/forms.py LoginForm accepts either email or username, resolves the user,
then calls Django authenticate with the email username field and password.
users/views.py login_view calls login() after valid form authentication and
redirects to problems:problem_list.

Logout
------
logout_view calls Django logout() and redirects to home. It is currently
reachable by GET at /users/logout/.

Password reset: current secure dependency
------------------------------------------
1. User submits email and new password to /users/reset-password/.
2. The view verifies that a Users row exists for that email.
3. It generates a six-digit OTP with get_otp(), stores reset OTP, expiry,
   attempt count, email, and an already-hashed new password in the session.
4. Resend sends the OTP using the existing Resend helper.
5. User submits the OTP to the same view.
6. verify_otp checks expiry, maximum attempts, and exact OTP equality.
7. On success, the existing user's password is replaced with the pending
   hashed password and the session is flushed.

Do not replace this flow with email-only password reset. It must continue to
require the OTP until a reviewed, secure alternative is deliberately designed.
PasswordResetToken and EmailVerificationToken database models are not used by
these views.

OTP details
-----------
- get_otp uses random.randint(100000, 999999), not a cryptographic RNG.
- Registration OTP keys are otp, otp_expires_at, otp_attempts, pending_user.
- Reset keys are reset_otp, reset_expires_at, reset_attempts, pending_reset.
- Expiry is five minutes using time.time()+300.
- Maximum wrong attempts is three.
- The OTP template has a Resend OTP button, but no resend-otp POST branch is
  implemented; that button is currently nonfunctional.

Authorization
-------------
login_required is used in profiles, submission history/detail, code execution,
and several discussion operations. Authorization coverage is incomplete and
must be reviewed before adding user-facing features.

6. PROBLEM SYSTEM
==================

Problem page workflow
---------------------
User opens /problems/<slug>
 -> problems.urls routes to problem_detail
 -> problems/views.py loads an active Problem by slug
 -> the template renders description, tags, companies, hints, samples, and
    editor controls
 -> static/js/problem_detail.js reads the selected language slug
 -> JavaScript sends code and language to run or submit endpoint
 -> submissions/views.py resolves the Problem and Language
 -> submissions/judge.py calls Judge0 through submissions/judge0.py
 -> results are returned as JSON and rendered in the browser
 -> submit mode creates Submission and SubmissionResult rows.

Problem list and detail
-----------------------
problem_list filters active Problems and calculates user solved counts and
basic difficulty counts. problem_detail loads active Problem, tags, sample
TestCases, previous/next problems, and renders templates/problems/problem_detail.html.
The detail template exposes language options with values python, java, cpp,
javascript, go, and rust. It does not currently show C in the option list even
though C is seeded as a Language.

Import source and command
-------------------------
Source workbook:
data/problems/import_data.xlsx

Command:
problems/management/commands/import_problems.py

Current behavior:
1. Calls Language.objects.get_or_create(slug=...) for the seven required
   languages. Existing records are not modified; missing rows are created with
   the documented name/version/Judge0 values.
2. Reads Problems and TestCases sheets using pandas.read_excel().
3. Uses Problem.objects.update_or_create(order_num=...) and updates title,
   description, and difficulty.
4. Uses TestCase.objects.update_or_create(problem=..., order_num=...) and
   updates input, expected output, sample flag, and explanation.
5. Re-running is intended to be idempotent for these records.

The command does NOT import or create tags, companies, ProblemTag,
ProblemCompany, hints, CodeTemplates, Editorials, DailyChallenges, submissions,
discussions, user data, or study plans.

Deployment dependency note
--------------------------
The Excel import requires both pandas and openpyxl. Both are pinned in
requirements.txt. Removing either can break Render deployment.

7. CODE EXECUTION AND JUDGE0
============================

Frontend
--------
static/js/problem_detail.js defines getSelectedLanguage(), which reads the
value of #language-select and defaults to python. Run sends JSON to:
/submissions/run/<problem slug>/
Submit sends JSON to:
/submissions/submit/<problem slug>/
The payload includes code and language; submit also includes elapsed_seconds.
The template provides CSRF_TOKEN and the JavaScript sends an X-CSRFToken
header, although the backend currently marks these two views csrf_exempt.

Backend lookup
--------------
Both submission endpoints use Language.objects.get(slug=language_slug).
If the row is absent, they return "Language not found!" with HTTP 404.
After lookup, they resolve an active Problem.

Run flow
---------
- Requires login.
- Performs basic code safety and input-reading checks.
- Loads sample TestCases only.
- Calls judge.run_code for each sample.
- Returns JSON test_case_results.
- Does not create a Submission.

Submit flow
-----------
- Requires login.
- Resolves Problem and Language.
- Creates a pending Submission.
- judge_submission runs all test cases through Judge0 batch API.
- SubmissionResult rows are created until the first failure.
- Submission status/runtime/memory are updated.
- The frontend displays accepted count, total, statuses, and outputs.

Judge0 client
-------------
submissions/judge0.py uses requests. It submits single or batch code to the
configured JUDGE0_URL, optionally sends X-Auth-Token, polls until completion,
and returns Judge0 result dictionaries. JUDGE0_TIMEOUT controls the deadline.
Judge0 is an external remote executor; this Django process does not execute
submitted source code locally.

Confirmed execution limitation
------------------------------
submissions/judge.py maps Judge0 status ID 3 to accepted and stores stdout,
but the submit path does not compare stdout against the TestCase expected_output
before treating that test case as accepted. A program that executes successfully
but prints the wrong output can therefore be recorded as accepted. This is a
critical correctness/business-integrity issue and should be fixed before
trusting solved statistics or leaderboards.

Other execution concerns
------------------------
The code safety check is a lightweight pattern check only. Judge0 sandboxing,
resource limits, network policy, abuse limits, and exact production Judge0
configuration require operational verification.

8. EMAIL AND RESEND
====================

Django Gmail SMTP was removed because Render Free did not reliably support the
previous SMTP connection. OTP email now uses the official resend Python package
and the Resend HTTPS API.

Configuration
-------------
users/views.py loads:
resend.api_key = os.getenv("RESEND_API_KEY")

The API key must only exist in the environment. Never place its value in source,
fixtures, logs, documentation, or this file.

send_otp_email() sends:
- from: onboarding@resend.dev
- recipient: supplied user email
- subject: supplied by caller
- plain text body: Your OTP is: {otp}

Active callers
--------------
- Registration OTP code remains in users/views.py but is unreachable in the
  current temporary registration-bypass path.
- Password reset calls it with subject "Your OTP for Password Reset".

Failure behavior
----------------
The helper returns False when the API key is missing, an exception occurs, or
an error response is returned. Password reset then renders a generic form error
instead of continuing as if the email was sent.

Testing-domain limitation
-------------------------
Resend's onboarding@resend.dev sender is a testing-domain sender. It is not a
production arbitrary-recipient solution. The recipient restriction must be
confirmed from the Resend account, but the current design decision is to use a
verified custom domain before enabling unrestricted registration OTP again.
After domain verification, update the sender configuration and production
Resend settings deliberately; do not hardcode credentials.

12. KNOWN BUGS, PREVIOUS PROBLEMS, AND FIXES
============================================

12.1 Incorrect Git repository root
----------------------------------
Git was accidentally initialized from the parent directory at one point. That
caused unrelated sibling/user folders to appear in repository status and made
Git commands misleading. The correct project root is:
C:\Users\cutek\Desktop\my_projects\LeetcodeProject
Run Git commands from that directory. Do not reset or delete unrelated files.

12.2 Render Gmail SMTP problem
------------------------------
The original email implementation used Django Gmail SMTP with smtp.gmail.com,
port 587, TLS, and Gmail credentials. Render Free did not reliably support the
connection for arbitrary production OTP delivery. The active solution replaced
Django send_mail with Resend HTTPS calls and RESEND_API_KEY.

12.3 Resend testing-domain limitation
-------------------------------------
The active sender onboarding@resend.dev is a Resend testing sender. It cannot
be treated as a verified arbitrary-recipient production domain. A verified
custom domain and sender configuration are required before restoring normal
registration OTP for arbitrary users.

12.4 Production Language not found
----------------------------------
Problems and 120 TestCases were imported into production, but Language rows
were initially absent because import_problems.py originally imported only
Problem and TestCase. The frontend sent slugs such as python, java, cpp,
javascript, go, and rust; the backend looked up Language by slug and returned
Language not found when production had no matching row.

The fix was to add idempotent Language.objects.get_or_create(slug=...) calls
for the seven language definitions at the start of import_problems.py. This is
now part of the deployment command and does not delete or update existing rows.
It remains an architectural requirement: an empty production database must run
migrations and the import command, or otherwise seed these Language rows, before
execution can work. A manual one-time seed alone would be lost when recreating
the database.

12.5 pandas/openpyxl deployment issue
-------------------------------------
The import command uses pandas.read_excel() on data/problems/import_data.xlsx.
Pandas requires an Excel engine; openpyxl is explicitly pinned in
requirements.txt. Both packages must remain installed or the Render build/import
step can fail.

12.6 Temporary registration OTP bypass
--------------------------------------
Because production email could not send to arbitrary users, successful normal
registration was temporarily changed to create is_verified=True and redirect
to login. The old OTP generation/storage/verification/Resend code remains for
future restoration. Password reset was intentionally not weakened.

13. QA AND SECURITY AUDIT FINDINGS
==================================

The following are confirmed from source review. They are not a substitute for a
penetration test against an isolated staging deployment.

CRITICAL
--------

C1. Accepted status is not compared with expected output
- Affected: submissions/judge.py, run_code() and judge_submission().
- Issue: Judge0 successful execution status is mapped to accepted without a
  server-side stdout versus TestCase.expected_output comparison in submit flow.
- Why it matters: incorrect programs can receive accepted SubmissionResult
  rows and corrupt solved statistics, progress, and any future leaderboard.
- Status: Not fixed.
- Recommended next action: normalize output and compare it server-side for every
  test case before accepting; add tests for wrong output, whitespace, and errors.
- Reproduction: submit code that exits successfully but prints output different
  from the expected test-case output.

HIGH
----

H1. CSRF exemption on code execution endpoints
- Affected: submissions/views.py submit_code() and run_code().
- Issue: both are decorated with csrf_exempt despite being authenticated POST
  endpoints; run also consumes remote execution capacity and submit writes data.
- Impact: cross-site requests from an authenticated browser may trigger runs or
  submissions.
- Status: Not fixed.
- Recommended next action: remove csrf_exempt and keep the existing JavaScript
  CSRF header; add a CSRF rejection test.
- Reproduction: from an isolated attacker origin, attempt a cross-site POST while
  logged in and observe whether the endpoint accepts it.

H2. Unsafe production defaults
- Affected: leetcode_project/settings.py.
- Issue: DEBUG defaults True; SECRET_KEY has a local fallback; secure cookie,
  HSTS, SSL redirect, and CSP settings are not explicitly configured.
- Impact: detailed error leakage or insecure transport/session behavior if
  production environment variables/settings are missing.
- Status: Not fixed; actual Render overrides are not verified.
- Recommended next action: require production settings, set DEBUG=False, use a
  strong required SECRET_KEY, and configure HTTPS/cookies/HSTS after verifying
  Render proxy behavior.
- Reproduction: run manage.py check --deploy and inspect the reported warnings;
  test the deployed environment separately.

H3. Public user directory exposes personal data
- Affected: users/views.py user_list(), users/urls.py, users_list.html.
- Issue: /users/ has no authentication/staff restriction and renders user data
  including email/mobile-related fields in the template.
- Impact: scraping, enumeration, privacy exposure, and phishing targeting.
- Status: Not fixed.
- Recommended next action: restrict/remove the directory and minimize public
  fields.
- Reproduction: request /users/ without authentication.

H4. Temporary registration bypass verifies arbitrary email addresses
- Affected: users/views.py register_view().
- Issue: new users are created with is_verified=True without proving control of
  the email address.
- Impact: unverified/third-party email accounts can be created.
- Status: Intentional temporary decision; not a permanent security fix.
- Recommended next action: restore registration OTP after a verified Resend
  domain is available.
- Reproduction: register using an address the registrant does not control.

H5. Premium entitlement enforcement is incomplete
- Affected: problems/views.py, premium/views.py, premium models.
- Issue: premium fields/models exist, but problem access/execution does not have
  a complete subscription entitlement check; premium endpoint is placeholder.
- Impact: paid/premium restrictions cannot be relied upon.
- Status: Not fixed; feature is incomplete.
- Recommended next action: centralize entitlement checks and test every premium
  access path before accepting payments.

MEDIUM
------

M1. Password-reset account enumeration
- Affected: users/views.py reset_password() and ForgotPasswordForm flow.
- Issue: "No account found with this email." distinguishes existing users.
- Impact: attackers can enumerate registered email addresses.
- Status: Not fixed.
- Recommended next action: use a generic response and rate-limit requests while
  preserving OTP security.

M2. OTP generation is not cryptographically strong
- Affected: users/views.py get_otp().
- Issue: uses random.randint rather than secrets-based generation.
- Impact: weaker OTP unpredictability if session/email controls are also weak.
- Status: Not fixed.
- Recommended next action: use a cryptographic random generator, hash or
  otherwise protect stored OTPs, and rate-limit attempts.

M3. OTP values are stored in plaintext session data
- Affected: users/views.py registration/reset session keys.
- Issue: raw OTP is placed in session storage.
- Impact: session-store compromise can reveal active OTPs.
- Status: Not fixed.
- Recommended next action: store a hash and compare securely; retain expiry and
  attempt limits.

M4. No meaningful rate limits on authentication or execution
- Affected: login, registration, password reset, run_code, submit_code, and
  discussion actions.
- Issue: application source does not implement request throttling for these
  flows.
- Impact: brute force, email abuse, Judge0 cost/resource abuse, and database
  pollution.
- Status: Not fixed.
- Recommended next action: add proxy/application rate limits and tests.

M5. Raw exception text is returned to submission clients
- Affected: submissions/views.py broad exception handlers.
- Issue: response includes str(e).
- Impact: implementation/database/provider details may leak.
- Status: Not fixed.
- Recommended next action: log server-side with a correlation ID and return a
  generic client error.

M6. Logout is a GET operation
- Affected: users/views.py logout_view(), users/urls.py.
- Issue: state-changing logout is reachable through GET.
- Impact: unwanted logout via links or image/navigation requests.
- Status: Not fixed.
- Recommended next action: use POST with CSRF protection.

LOW
---

L1. Resend OTP button is displayed but not implemented
- Affected: templates/users/otp_form.html and users/views.py.
- Status: Not fixed; intentionally separate from the email migration task.
- Recommended next action: implement a rate-limited resend flow only after
  deciding on the verified-domain email design.

L2. Course URL module is not included at the root
- Affected: courses/urls.py and leetcode_project/urls.py.
- Impact: course route is unreachable through the normal root URLconf.
- Status: Not fixed.

L3. Admin coverage is partial
- Several domain models have no admin registration.
- Status: Not fixed; verify intended administration workflow before adding.

The following areas require focused tests or a staging penetration test. They
are not asserted as vulnerabilities solely because they are listed here:
- IDOR and ownership checks for every profile, submission, discussion, note,

  output, including all JavaScript innerHTML rendering paths.

- Database race conditions around duplicate registration, import reruns, and
  duplicate contest/submission operations.

  and profile pages.
- Production backups, monitoring, error tracking, and alerting.
